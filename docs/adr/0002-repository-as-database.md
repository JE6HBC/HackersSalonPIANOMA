# ADR-0002: リポジトリをデータベースとして使う

- **状態:** 採用
- **日付:** 2026-09-22

## 背景

[ADR-0001](0001-github-only-stack.md) でサーバを持たないと決めた以上、
イベント情報・参加者・受賞歴・AI課題をどこに置くかを決める必要がある。

このリポジトリで扱うデータには、共通の性質がある。

- **量が少ない**（1回30人 × 月1回）
- **更新頻度が低い**（イベント当日以外はほぼ動かない）
- **人が読んで意味が分かる**（イベント名、課題文、受賞コメント）
- **レビューされるべき**（誰がいつ何を書いたかが残ってほしい）

## 決定

**`data/` 配下のJSON / Markdownファイルを唯一の正とする。**
更新はPull Request経由でのみ行い、スキーマは `src/content.config.ts` の Zod で
ビルド時に検証する。

- 1イベント = 1ディレクトリ（`data/events/YYYY-MM-DD/`）
- ファイル間の参照（受賞者が参加者に存在するか等）は `scripts/validate-data.mjs` がCIで検証
- 人が直接編集することを前提に、整形はPrettierに任せる

## 却下した案

| 案                                     | なぜ選ばなかったか                                                                    |
| :------------------------------------- | :------------------------------------------------------------------------------------ |
| SQLite をリポジトリにコミット          | 差分がバイナリになりレビューできない。PRで課題を投稿する、という入口が死ぬ            |
| GitHub Issues をデータストアにする     | 構造化されたデータの表現に向かない。取得にAPIとトークンが要り、静的ビルドから読めない |
| すべてをMarkdownのfront matterに寄せる | 参加者リストのような配列データが書きづらく、壊れやすい                                |
| スキーマを JSON Schema で別管理        | Zodと二重管理になる。編集時の補完は得られるが、ズレたときに誰も気づけない             |

## 結果

**得たもの**

- AI課題やレポートの投稿が、そのままPull Requestという貢献の形になる
- 壊れたデータは `npm run build` が落ちるので本番に出ない
- 「誰がいつこの受賞を記録したか」が `git log` で追える
- バックアップが不要（全員のクローンがバックアップ）

**失ったもの / 注意点**

- リアルタイム更新ができない。当日の変更は [ADR-0004](0004-event-day-state-in-browser.md) の方式で扱う
- 参加者が数百人規模になるとレビューが現実的でなくなる。その時は再検討する
- IDの変更が破壊的変更になる。`event.id` / `participant.id` / `award.id` / `challenge.id` は変えない
