# ADR-0004: 当日の状態はブラウザに置く

- **状態:** 採用
- **日付:** 2026-09-22

## 背景

イベント当日には、リポジトリに入れるには速すぎる変化がある。

- 受付での参加者追加とチェックイン
- トーナメントの残り時間、今どのラウンドか

[ADR-0001](0001-github-only-stack.md) により書き込み先のサーバはなく、
GitHub Pages への反映にもビルドで1〜3分かかる。タイマーには使えない。

## 決定

**当日の可変状態はブラウザの `localStorage` に持ち、イベント後にPull Requestでリポジトリへ戻す。**

- 参加者の追加・チェックイン（`/admin`）→ `localStorage` → JSON書き出し → PR
- タイマーの進行状態（`/signage/timer`）→ `localStorage`
- 同一ブラウザの別ウィンドウ間は `BroadcastChannel` で同期する
  （操作用ウィンドウ ＋ プロジェクタ投影用ウィンドウ、という使い方を想定）
- 残り時間は経過秒の加算ではなく**終了時刻(epoch ms)との差**で計算する。
  タブが非アクティブになって `setInterval` が間引かれてもズレない
- `localStorage` の読み書きは必ず try/catch で囲む。プライベートモードで例外が飛ぶ

## 却下した案

| 案                               | なぜ選ばなかったか                                                             |
| :------------------------------- | :----------------------------------------------------------------------------- |
| WebRTC / WebSocket で端末間同期  | シグナリングサーバが要る。ADR-0001に反する                                     |
| 状態をURLのクエリに入れて共有    | タイマーのような連続的に変わる状態には使えない                                 |
| 当日もPR経由で反映する           | ビルド待ちで進行が止まる。受付の行列が伸びる                                   |
| サービスワーカーで共有状態を持つ | 同一オリジン内でしか動かないのは `BroadcastChannel` と同じで、複雑さだけ増える |

## 結果

**得たもの**

- ネットが落ちてもタイマーは動き続ける（ページさえ開いていれば）
- 受付がGitHubのビルドを待たない
- 参加者の入力内容が、イベント中はその端末の外に出ない

**失ったもの / 注意点**

- **別のPC・別のスマホとは同期しない。** 会場スクリーンと操作端末は同じPCで開くこと
- ブラウザのデータを消すと当日の入力が消える。書き出す前に消さないこと
- 共用PCを使った場合、イベント後に「この端末の追加分を破棄」を押す運用が必要
  （→ [運用手順](../operations-runbook.md)）
