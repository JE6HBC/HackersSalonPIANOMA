# アーキテクチャ

## 一言でいうと

**外部サービスを使わず、GitHubの機能だけで完結させる静的サイト。**
データベースの代わりにGitリポジトリを、管理画面の代わりにPull Requestを使う。

```
                         ┌─────────────────────────────────────────┐
   参加者               │  GitHub (JE6HBC/HackersSalonPIANOMA)    │
   ─────                │                                          │
   Issue Form ─────────▶│  Issues ──▶ Actions ──▶ 自動PR           │
   （参加登録）          │                            │              │
                         │                            ▼              │
   コントリビューター     │                     ┌──────────┐         │
   ─────────────        │  Pull Request ─────▶│  main    │         │
   PR（課題・レポート）  │      ▲ レビュー      │  data/   │◀── 唯一の正
                         │      │              │  src/    │         │
   運営                  │      │              └────┬─────┘         │
   ────                  │      │                   │ push           │
   /admin で登録 ────────┼──────┘                   ▼                │
   （localStorage）      │                  Actions: build           │
   JSON書き出し          │                          │                │

                         └──────────────┬───────────────────────────┘

                     ▼                  ▼                  ▼
```

## 技術スタック

| 層           | 採用                                       | 理由                                                                                        |
| :----------- | :----------------------------------------- | :------------------------------------------------------------------------------------------ |
| サイト生成   | [Astro](https://astro.build) 5（静的出力） | Markdown/JSONをそのままコンテンツとして扱え、スキーマ検証が組み込み。JSは必要な所にだけ出る |
| 型           | TypeScript（strict）                       | データ構造が育つ前提なので、壊れたら気づける状態にしておく                                  |
| スキーマ     | Zod（`src/content.config.ts`）             | データの形の唯一の正。ビルド時に検証され、壊れたデータは本番に出られない                    |
| スタイル     | 素のCSS + カスタムプロパティ               | 依存を増やさない。サイネージは独自の巨大タイポが必要でユーティリティの旨みが薄い            |
| 状態（当日） | `localStorage` + `BroadcastChannel`        | サーバがないため。同一ブラウザ内の複数ウィンドウは同期する                                  |
| CI           | GitHub Actions                             | 整形・データ整合性・型・ビルドを全PRで検証                                                  |
| 配信         | GitHub Pages                               | GitHub Pro の範囲内。独自ドメインも当てられる                                               |

**依存パッケージは Astro と Prettier だけ**です。増やすときはPRに理由を書いてください（[CONTRIBUTING.md](../CONTRIBUTING.md) 6章）。

## できること / できないこと

この構成を選んだ以上、できないことがあります。**運営フローのほうを、できないことに合わせて設計しています。**

### できること

- 開催予定・アーカイブ・AI課題・受賞歴の公開（PRで誰でも更新提案できる）
- GitHubアカウントを持つ人のオンライン事前登録（Issue → 自動PR）
- 会場スクリーンへの進行表示（現在のプログラム・卓・人数）
- トーナメントの時間管理（ラウンド・休憩・残り時間の大画面表示）
- 当日の会場登録とチェックイン（運営端末のブラウザ内で完結、後からPRで反映）
- 全変更の履歴とレビュー（Gitがそのまま監査ログになる）

### できないこと（と、その回避策）

| できないこと                                 | なぜ                                                                               | 当日どうするか                                                                                             |
| :------------------------------------------- | :--------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------- |
| **GitHubアカウントのない人のオンライン登録** | 静的サイトはPOSTを受けられず、ブラウザからGitHub APIを叩くにはトークンの露出が必要 | 当日会場で `/admin` から運営が代理登録する。事前に人数だけ知りたい場合はSNSの返信で数える                  |
| **複数の端末・スマホ間でのリアルタイム同期** | 共有状態を置くサーバがない                                                         | タイマーは「操作用ウィンドウ」と「投影用ウィンドウ」を**同じPCで**開く。参加者のスマホには進行を同期しない |
| **その場で即座に本番サイトへ反映**           | Pagesのビルドとデプロイに1〜3分かかる                                              | 当日の可変情報（誰が来たか等）はサイネージのブラウザ内で扱い、サイトへの反映はイベント後のPRで行う         |
| **模範回答をイベント当日まで確実に隠す**     | 静的HTMLに含めた時点でソースを見れば読める                                         | 伏せたい課題は front matter の `draft: true` のままにし、イベント後にPRで `false` にする                   |
| **参加者ごとのログイン・マイページ**         | 認証基盤がない                                                                     | GitHubアカウント名で紐づけて表示するだけに留める                                                           |
| **申込みのキャンセル待ち・決済**             | 同上                                                                               | 定員はIssueの取り込み時にチェックし、超えたらコメントで知らせる。支払いは当日現地                          |

これらが本当に必要になったら、その時点で外部サービス（Supabaseなど）の導入をADRとして提案してください。
**先回りして入れないこと。** 今の構成の価値は、運営が1人でも止まらないことにあります。

## ディレクトリの責務

```
data/          イベントのデータベース。PRでのみ更新される唯一の正
docs/          設計・運用・方針。adr/ に「なぜそうしたか」の記録
scripts/       Node製のツール（検証・雛形生成・Issue取り込み）。依存なしで動くこと
src/
  content.config.ts   データスキーマ（唯一の正）
  lib/                データ取得・整形の共通処理。ページから直接 getCollection しない
  layouts/            BaseLayout（通常ページ） / SignageLayout（会場スクリーン）
  components/         再利用するUI部品
  pages/
    index, events/, challenges/, awards   公開ページ
    signage/                              会場スクリーン（大画面前提・noindex）
    admin/                                運営コンソール（当日用・localStorage）
  styles/       tokens.css（色・余白・文字）と global.css
.github/
  workflows/    ci.yml（検証） / deploy-pages.yml（配信） / registration-sync.yml（登録取り込み）
  ISSUE_TEMPLATE/  参加登録・LT・課題投稿・不具合・提案
```

## データの流れ

1. **編集** — `data/` のファイルをPRで変更する（人でも、Actionsでも）
2. **検証** — CIが `validate:data`（ファイル間参照・個人情報）と `astro check`（型）とビルドを回す
3. **レビュー** — CODEOWNERSが割り当てられ、人が中身を見る
4. **マージ** — `main` にSquash mergeされる
5. **配信** — `deploy-pages.yml` がビルドしてGitHub Pagesへ
6. **表示** — サイト・サイネージ・タイマーが同じデータを読む

「当日その場で変わる情報」だけがこの流れの外にあり、ブラウザの `localStorage` に置かれます。
それはイベント後に 4 の流れに戻ってきます（[運用手順](operations-runbook.md)）。
